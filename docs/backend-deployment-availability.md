# 백엔드 배포 중 API 연결 유지

기존 배포는 사전 검사한 후보를 제거하고 운영 컨테이너를 다시 생성했다
프론트 Nginx가 이전 Docker 주소를 기억하면 새 백엔드가 준비된 후에도 요청이 실패할 수 있었다

백엔드 배포는 후보를 유지한 채 다음 순서로 진행한다

1. 현재와 같은 비루트 이미지로 후보를 실행하고 Django 설정을 검사
2. DB 백업과 migration 수행 후 후보의 `/healthz`에서 DB·Redis `ok` 확인
3. 후보의 `/api/v1/auth/me`가 JSON과 HTTP 401을 반환하는지 확인
4. 프론트의 기존 API·health·내부 secret 경로를 후보 주소로 전환하고 이전 Nginx worker 종료 대기
5. 운영 백엔드만 다시 생성하고 DB·Redis·인증 API 확인
6. 원래 프록시 설정으로 Nginx를 reload해 새 Docker 주소를 해석하고 후보를 쓰던 worker 종료 대기
7. 외부 HTTPS 검사와 배포 SHA 기록이 끝난 후 후보 제거

프론트 컨테이너, PostgreSQL, Redis는 재시작하지 않는다
원래 프록시 경로와 내부 secret 경로의 접근 제한은 그대로 복사한다
후보는 CPU 1개, 메모리 768MiB, 프로세스 128개로 제한한다
배포 간에는 호스트의 같은 flock을 사용하며 완료되지 않은 전환 기록이 있으면 새 배포를 중단한다
공용 호스트의 전체 이미지나 빌드 캐시를 prune하지 않고 해당 구성요소의 배포 이미지 태그만 정리한다

## 실패와 복구

새 운영 백엔드가 준비되지 않으면 후보로 요청을 계속 전달하면서 이전 이미지로 운영 백엔드를 복구한다
롤백 전에 후보 경로를 다시 확인하므로 Nginx reload가 일부만 끝난 경우에도 운영 백엔드를 먼저 종료하지 않는다
롤백한 운영 백엔드가 DB·Redis·인증 검사를 통과하고 Nginx worker가 종료된 뒤에만 후보를 제거한다

롤백이나 Nginx 상태를 확인할 수 없으면 배포를 실패 처리하고 후보, 원래 설정, 전환 상태를 보존한다
신호로 배포가 중단돼도 서비스 중일 수 있는 후보를 EXIT에서 강제 제거하지 않는다
상태 파일은 `/opt/msg-dev/deploy-state/backend-bridge.json`, 원래 설정은 같은 디렉터리의 `backend-bridge.nginx.conf`다
이 상태에서는 프론트 재배포도 차단해 후보를 경유하는 경로가 사라지는 것을 막는다

관리자는 같은 `/var/lock/msg-dev-deploy.lock`을 잡고 검토한 helper로 `hold`, `ready`, `finish`를 수행한다
`hold`는 보존된 후보로 경로를 돌리고 기존 worker 종료를 기다린다
`ready --container <운영 컨테이너 ID>`는 실제 DB·Redis·인증 응답을 확인한다
`finish --container <운영 컨테이너 ID>`는 원래 경로를 복원하고 후보를 사용하던 worker 종료를 기다린다
각 명령에는 `--domain msgctf.kr`을 전달한다
finish 성공 후에만 해당 전환 기록에 적힌 후보 컨테이너를 제거한다
상태 파일을 지우거나 후보를 먼저 정리하는 방식으로 새 배포를 통과시키지 않는다

## 검증 범위

CI는 실제 Docker와 Nginx를 격리한 네트워크에서 실행하고 운영 역할 컨테이너가 없는 동안 후보의 HTTP 응답을 연속 확인한다
교체 성공, 실패한 운영 백엔드, 이전 버전 복구, Nginx reload 실패, worker 종료 지연, 프론트 컨테이너 교체를 검사한다
이 격리 검사는 전환 동작을 검증하며 실제 PostgreSQL·Redis 연결 검증을 대신하지 않는다
운영 전환에서는 실제 앱의 `/healthz`와 인증 API 응답을 사용한다

이 방식은 기존 버전과 새 버전이 동시에 서비스할 수 있는 호환 migration을 전제로 한다
긴 DDL 잠금, 파괴적인 schema 변경, 외부 DB·Redis 장애를 무중단으로 처리한다고 보장하지 않는다
DB를 자동으로 되돌리지 않으며 코드 롤백이 새 schema와 호환되지 않으면 후보를 유지하고 관리자 확인을 요구한다
프론트 자체를 교체하는 작업의 무중단 전환은 이 변경의 범위에 포함되지 않는다
